# Повторная проверка ФТ-1–57 после перехода на контракт БД Python

Дата: 30 октября 2026 года.

Проверено текущее рабочее дерево `znac-expo`, включая незакоммиченные изменения. Основание — приложенный список ФТ и последующие решения из переписки. Исходный аудит проводился без изменений кода; затем по ответам пользователя реализованы ФТ-4, 6, временный вариант ФТ-42–43, а также ФТ-49, 56 и 57. Таблица обновлена по итогам реализации.

После реализации пройдены 230 автоматических тестов, TypeScript и ESLint. Проверены Elapsed, предупреждение о любых правках предыдущего месяца и экспорт одного месяца/диапазона через границу года без изменения исходной базы. Веб-проверка компонентов подтвердила скрытие Total Break, удаление отдельного перерыва, состояния плеера и выбор периода. Штатные тесты также включают сверку SQL с Python, переход с двух вариантов Python v6 на v7 и чтение/изменение общего файла реальным Python-репозиторием. Шесть диагностических сценариев исходного аудита использовались для выявления ограничений; их успешность не означала выполнения ФТ-9 и ФТ-11.

Используются только три статуса: «выполнено», «частично выполнено», «не выполнено». Статус отражает реализацию с учётом согласованных уточнений. Необходимость согласования, проверки на устройстве и прочие ограничения указаны отдельно в комментариях.

Физический iPhone, Android и нативное системное меню передачи файла в этой проверке не использовались. Статус «выполнено» подтверждён по коду и применимым автоматическим проверкам; он не означает, что проведена отдельная проверка каждого визуального требования на телефоне.

## Уточнения, имеющие приоритет над исходным файлом

- ФТ-7: Play очищает только End завершённого дня; сохраняет Start, перерывы и параметры. После продолжения доступны действия работающего либо приостановленного дня.
- ФТ-9: порог считается по фактическому времени между Start и Stop, а не по смене минут. Реализация точного порога пока отложена; то же ограничение точности есть у ФТ-11.
- ФТ-21: закрывать можно текущий и прошлые месяцы.
- ФТ-26: No data и параметры дня сохраняются после переоткрытия.
- ФТ-32: предыдущий исправленный месяц нужно снова закрыть; открытый предыдущий месяц даёт нулевой Carryover.
- ФТ-36: свободный ввод типа, включая No data; норма и её ручное переопределение обрабатываются как в Python. Regular day — тип; filled/not filled — состояние заполненности для цвета, а не отдельные типы. Заполненный рабочий день зелёный, незаполненный фиолетовый.
- ФТ-40: поведение открытого перерыва определяется Python. Python допускает один незавершённый интервал; его можно завершить или удалить вручную.
- ФТ-42–43: последнее решение пользователя — временно скрыть Total Break и его редактор за жёстким false-флагом, сохранив код для Python-разработчика. В Expo остаются интервалы. Совместное хранение двух способов не включается; общий контракт Python v7 сохраняется.
- ФТ-48: полная очистка всех пользовательских данных дня, восстановление значений по расписанию и сброс сегодняшнего плеера без записи Stop.
- ФТ-49: подтверждено удаление каждого перерыва отдельно, как уже реализовано. Общая кнопка удаления всех перерывов не требуется.
- ФТ-55: импорт целой базы по образцу Python. Общий контракт v7 уже подготовлен, но замена активной базы ещё не реализована.
- ФТ-56: подтверждены отдельный полный экспорт и непрерывный диапазон целых месяцев, минимум один месяц. Произвольные даты исключены из текущей версии.
- Контракт БД — Python v7. Старая тестовая база Expo пересоздаётся без переноса данных. Локальные настройки интерфейса хранятся отдельно от общей базы, аналогично QSettings в Python.

## Главные результаты

1. Нарушений схемы Python v7, сохранности результатов закрытых месяцев и изоляции последующих месяцев проверками не обнаружено.
2. ФТ-9 и ФТ-11 не выполнены для фактических интервалов короче 60 секунд, пересекающих границу минуты.
3. В ФТ-21 есть незавершённый сценарий интерфейса: закрытие из Календаря при устаревшем сохранённом Carryover отклоняется после успешного предварительного расчёта. Обновление Календаря это не исправляет; требуется открыть целевой месяц на главном экране. Защита репозитория работает правильно и не меняет данные частично.
4. ФТ-55 пока ограничен проверкой выбранного файла. Импорта с заменой активной базы нет.
5. ФТ-57 исправлен: предупреждение учитывает любые пользовательские изменения дня, включая только Vacation, ручную норму и последующую очистку. Автоматически созданные дни и обновление их норм по расписанию не считаются пользовательским заполнением.
6. По последнему решению ФТ-42–43 временно выполнены скрытием Total Break и его редактора за жёстким `SHOW_TOTAL_BREAK = false`. Код сохранён для Python-разработчика. В Expo остаются интервалы; контракт БД не менялся. Отображение суммы по исходному ФТ-41 на это время отсутствует.

## Воспроизведённые ограничения

### 1. ФТ-9: фактические две секунды работы сохраняются

1. Нажать Start в 09:00:59.
2. Нажать Stop в 09:01:01.
3. Сейчас сохраняются start_minute=540 и end_minute=541.

Причина: плеер передаёт минуты, а операции репозитория не используют передаваемый `now` для определения фактической длительности. Проверяется равенство минут. Исправление только равенства минут не реализует согласованный порог 60 секунд.

### 2. ФТ-11: фактические две секунды паузы сохраняются

1. На работающем дне нажать Pause в 12:00:59.
2. Нажать Resume в 12:01:01.
3. Сейчас сохраняется интервал 720–721 и учитывается одна минута Break.

Причина та же: минутная точность вместо фактической длительности. В той же минуте Resume работает сразу и удаляет короткую паузу, но пересечение границы минуты меняет результат.

### 3. ФТ-21: preview и закрытие при устаревшем Carryover

1. Создать октябрь, пока сентябрь ещё открыт: в октябре сохранён Carryover=0.
2. Закрыть заполненный сентябрь с итогом +01:00.
3. В Календаре получить предварительный расчёт закрытия октября: он показывает Carryover=+01:00.
4. Подтвердить закрытие октября.
5. Репозиторий отклонит операцию: `The carry-over changed. Reload the month and review it before closing.`
6. Повторное чтение года в Календаре сохраняет старый Carryover=0. Открытие октября на главном экране актуализирует его, после чего закрытие успешно.

Это корректная защита от закрытия с неактуальным сохранённым балансом, совпадающая с Python-репозиторием. Нужен законченный путь в интерфейсе: объяснить необходимость обновления целевого месяца и дать перейти к нему на главном экране, затем повторить предварительный расчёт/подтверждение. Не следует устранять проверку в БД или обновлять все месяцы года.

### 4. ФТ-57: значение «заполненная карточка» — исправлено

Проверены три состояния предыдущего открытого месяца:

| Данные дня                        | Предупреждение сейчас |
| --------------------------------- | --------------------- |
| Только Vacation | Да |
| Vacation и ручная норма 120 минут | Да |
| Добавлен Start                    | Да                    |

Получен ответ: любые пользовательские изменения дня требуют предупреждения. Только автоматически созданная норма и календарный Weekend без ручных правок не означают пользовательское заполнение. После закрытия месяца предупреждение исчезает.
